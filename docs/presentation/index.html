02 / 10 - The business problem

Evidence gathering is the bottleneck, not judgment

A UK personal motor pricing analyst weighing a renewal-portfolio action needs claims, conversion, competitor, and market-intelligence evidence pulled together before they can even start reasoning about whether to act.

Scattered sources

Claims performance, conversion and retention, competitor pricing, pricing history, market reports, broker notes, and aggregate customer feedback live in different places with different freshness.

Manual synthesis

Pulling it together, checking it for contradictions, and writing a defensible rationale is slow, repetitive, and easy to do inconsistently under time pressure.

Accountability must stay put

Whatever accelerates this cannot quietly become the decision-maker. The analyst's judgment and sign-off are the point, not an inconvenience to automate away.

Framing~90s

03 / 10 - What this is not

Three things this deliberately refuses to be

Not a pricing engine

No code path in this repository can execute a pricing change. Every recommendation is decision support pending analyst review.

Not trained on real data

Every dataset is synthetic, seeded, and reproducible. No Aviva systems, customer data, or proprietary pricing models are used or imitated.

Not a single model's opinion

Recommendation synthesis, evidence gathering, and governance review are three separate agents with three separate jobs - none of them grades its own work.

05 / 10 - Governance in depth

Every control is code, not a prompt instruction

Deterministic math

Loss ratios, movement percentages, and every clamp are computed by plain Python. The model narrates already-computed numbers - it cannot hallucinate a figure.

Policy clamp

No recommendation can propose more than a ±5% movement, enforced in code, independent of what any agent argues for.

Document quarantine

Retrieved documents are untrusted data. Prompt-injection content is stripped before it ever reaches a model call.

Bounded execution

Every agent run has enforced turn limits, tool-call limits, timeouts, and a bounded retry count - no runaway loops.

See README - Governance and observability controls~90s

06 / 10 - Evidence and citations

Nothing is asserted without a citation

Every material claim in a recommendation resolves to a specific evidence-ledger entry: source type, date, identifier, and the metric it supports.

  • Counter-evidence is rendered as a prominent warning block, not buried beneath the recommendation - an analyst sees the case against the action as clearly as the case for it.
  • Confidence is reported as five separate components (evidence coverage, source freshness, specialist agreement, data quality, conflict penalty), not one opaque score.
  • Fair-value status flags when a recommendation needs closer review before rollout, with named follow-up actions.

09 / 10 - Delivery approach

Built ticket by ticket, by a coding agent, against a written spec

  • Every ticket got its own implementation plan document before any code was written.
  • Strict TDD throughout: failing test, verified red, minimal implementation, verified green, commit - repeated per logical unit.
  • A full quality suite (lint, strict type checking, the full test suite, a security scanner, and a secret scan) gates every commit.
  • End-to-end UI tests exercise the actual rendered interface, not just service-layer logic underneath it - this caught and fixed two real bugs during this ticket alone.

10 / 10 - Roadmap and commercial framing

From prototype to platform, one earned step at a time

Prototype - this

Synthetic data, three designed scenarios, full governance and evaluation harness. Proves the architecture and the guardrails.

Shadow mode

Run alongside human analysts on real (governed-access) data with no influence on outcomes. Measure agreement rate and time-to-first-recommendation as hypotheses to be tested, not savings to be assumed.

Limited pilot

A small analyst cohort, human-in-the-loop only, with the same decision-record and governance controls proven here.

Platform scale

Only after shadow-mode and pilot evidence justifies it - the data warehouse and decision-audit swap points are already designed into the contracts.

Commercial value is a measurement plan, not a number: "time-to-first-recommendation reduced by X%, to be measured" - never an invented saving or loss-ratio figure.

Appendix A - Data model

Four structured sources, one unstructured corpus

Structured (DuckDB, versioned)

Claims, conversion, competitor, and pricing-history monthly records, materialized into a persistent, checksum-verified, versioned analytics database with an explicit permitted-column allowlist per source.

Unstructured (BM25-retrieved)

Market reports, repair-cost intelligence, broker notes, and aggregate customer feedback - retrieved, quarantined against injected content, and cited by document ID.

Appendix B - Prompt-injection defense

Defense in depth, measured, not assumed

  • quarantine_unsafe_documents strips flagged content from retrieved documents before any model call sees it.
  • The chat layer refuses raw SQL, customer-level requests, protected-attribute use, and direct override attempts with a plain-language explanation, before any retrieval happens.
  • Four dedicated golden-set cases exercise document-embedded injection, direct override, data exfiltration, and raw-SQL attempts.
  • Measured result on the last live run: 0% success across all four.

Appendix D - Coding-agent delivery model

One ticket, one plan, one TDD cycle at a time

  • Each GitHub issue is implemented from a written plan document under docs/superpowers/plans/, produced before any code is touched.
  • Every logical change follows: write the failing test, confirm it fails for the right reason, implement the minimal fix, confirm it passes, commit.
  • The full quality suite (lint, strict types, tests, security scan, secret scan) runs before any ticket is considered closed.
  • Manual browser verification supplements automated tests for anything genuinely visual or interaction-order-dependent - this is exactly what caught the two UI bugs fixed while building this deck.

Appendix F - Production architecture

The swap points are already designed into the contracts

Analytics store

PersistentAnalyticsDatabase would be replaced by a read replica of the real pricing data warehouse, behind the same typed query_source interface used today.

Decision audit

The SQLite decision store would be replaced by the real underwriting decision-audit system - DecisionRequest/AnalystDecision are already shaped for that swap.

Model routing

A single Azure OpenAI dev deployment would move to production model routing, rate limits, and regional failover.

What stays the same

The typed contracts, the governance checks, the evidence ledger, and the evaluation harness - the parts that make this trustworthy do not change with scale.
